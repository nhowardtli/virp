# SW-3850 Credential Fix — devices.json revert + socket_allowed_uids correction

**Date:** 2026-05-16
**Trust primitive:** primarily a data fix (`/etc/virp/devices.json.age` content). Secondary W3 (`socket_allowed_uids`) correction.
**Author:** Nate Howard + Claude Code
**Scope:** all 40 VIRP devices were affected; SW-3850 was the case that surfaced first.

---

## Summary

Dashboard tool calls to SW-3850 (and, by inspection, all 40 devices in
current config) were failing with `[Cisco] All auth methods failed for
@10.0.10.2` — note the empty username before `@`. libssh2 was being
called with `username=""` because the credential field was absent in
`/run/virp/devices.json`.

Root cause: an incomplete schema migration. Between two 2026-05-14
00:13 backups of `/etc/virp/devices.json.age`, the per-device schema
was changed from inline credentials (`username` / `password` /
`enable`) to `credential_ref: "<name>"` pointers — but:

1. The credential store (`/etc/virp/creds.d/`) was never created.
2. The O-Node loader (`src/virp_onode_prod.c`) has zero handling for
   `credential_ref` — `grep -r credential_ref /root/virp/src` is empty.
3. All 40 devices in the post-migration config therefore had no
   resolvable credentials. Daemon left `username`/`password` NULL;
   libssh2 sent empty-string user; servers rejected.

Fix: pure revert to `.bak.20260514-001349` content (43 devices,
inline credentials, restoring 3 inadvertently-removed devices —
Proxmox-Colo, Wazuh, srx-300 — and correcting two node_id values
that were apparently corrupted in the same migration: ASA-5525
`A0100201 → 0A0000FD` (hex of 10.0.0.253 mgmt IP), fortiwifi-60f
`F0100101 → C0000001`).

A secondary regression surfaced after the first re-encrypt: the
backup's `socket_allowed_uids` array was `[0, 998]` — values that
made sense at the time the backup was taken (socat running as root or
as a dedicated `virp-socat` user) but are no longer valid after
tonight's W3 fix moved socat to uid 999 (virp-onode). The W3 gate
correctly rejected uid 999 with "not in socket_allowed_uids". Fixed
by editing `socket_allowed_uids` to `[999]` and re-encrypting a
second time. W3 invariant restored.

W1, W2, W4 unchanged.

## Significance

Two structurally distinct issues, both surfaced and fixed tonight:

**1. Broken schema migration.** Someone (or some tooling) wrote
`credential_ref` entries into devices.json that the daemon doesn't
understand. The credential store this points to does not exist on
disk. The loader code that resolves it does not exist in the
checked-in source. This is a half-finished migration — design intent
visible in the data, implementation missing from the code.

If/when the credential_ref pattern is genuinely wanted, the work
required is:
1. Build `/etc/virp/creds.d/` (mode 0700, root, per the existing
   deploy/virp-onode.service comment).
2. Patch `src/virp_onode_prod.c` to honor `credential_ref` →
   `/etc/virp/creds.d/<name>` lookup, with fall-through to inline if
   absent.
3. Migration tooling that writes both the ref and the store entry
   atomically.
4. Tests for missing ref, missing store entry, malformed entry.

Until then, inline credentials are the only working scheme. Anyone
who edits devices.json should leave `username` / `password` /
`enable` populated.

**2. Backup-restore as a regression vector.** The backup's
`socket_allowed_uids: [0, 998]` was correct *at the time the backup
was taken*. After tonight's W3 fix moved socat to uid 999, those
values became wrong. Restoring the backup verbatim reintroduced an
obsolete policy and bricked the socket gate for a window. Lesson:
**security-relevant fields are coupled across files** — a devices.json
restore must check that `socket_allowed_uids` still matches the
current socat user, and an OS-side change to the socat user must
remember to update devices.json. Worth a checklist item.

**3. Plaintext credential exposure during diagnosis.** My
secret-redaction regex (`password|secret|enable_password|...`) did
not include the bare key `enable`, so the ASA-5525 / SW-3850 enable
password (`Lab2001-...`) printed in a diff output earlier in the
session. The value was already in the user's session message and
therefore in the conversation log; the redaction failure echoed it
back once. **Per user threat model, that value should be considered
logged in this session and rotated if rotation is policy.** Going
forward: redaction regex now includes bare `enable` key (see
`Reference` section).
