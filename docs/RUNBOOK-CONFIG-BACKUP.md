# Config-backup-and-drift runbook

A scheduled, **no-AI** automation on virp-lab that demonstrates governed
action: every device interaction goes through the VIRP gate, every piece
of evidence is signed and chain-registered, and the one corrective
action it ever wants (restore a drifted config) is something it is
*structurally unable* to perform — it can only propose.

## What it does (hourly, `virp-config-backup.timer`)

For each FRR node (frr1–4):

1. **Backup** — submits `vtysh -c "show running-config"` through the
   gate. The command classifies GREEN, executes, and returns an
   O-Key-signed observation. The daemon chain-registers it (session
   `config-backup:<date>`), and the config + the raw signed bytes land
   in `/var/lib/virp/config-backups/<device>/<ts>.conf` / `<ts>.meta.json`
   (umask 0077 throughout).
2. **Diff against the established baseline**:
   - **No baseline** → alert `no_baseline`. The config is recorded but
     **never silently adopted** — see "Baselines" below.
   - **Identical** → a `no_drift` chain entry is registered; the
     daemon's signed CHAIN_ENTRY receipt is stored as evidence.
   - **Different** → the runbook writes a drift alert (journal +
     `alerts.jsonl`) and a unified-diff artifact
     (`drift-<ts>.diff`), then **files a gate proposal** to restore the
     baseline: it submits the generated revert command, which the linux
     classifier tiers RED, so the ENFORCE gate refuses execution and
     files a signed proposal instead. The rejection payload carries the
     `proposal_id`, which lands in the alert and in a `drift_alert`
     chain entry. **The device is never modified.**

Exit codes: `0` clean, `1` any alert (the unit shows failed — same
convention as the autopilot timers), `3` identity check refused.

## Identity model

Runs as **`virp-backup`**: a dedicated system account, member of **no**
group but its own. It is not the daemon user and not root; the daemon's
`socket_allowed_uids` includes it via the `${VIRP_BACKUP_UID}`
placeholder (virp-lab template only). Socket reach is granted by ACL
(`deploy/config-backup-access.sh`), *not* by joining group `virp`,
because group `virp` can read the rendered `devices.json` credentials.

At startup the script **refuses to run** (exit 3) if it is root, the
daemon user, a member of group `virp`, or if it can read ANY of:
`onode.key`, `chain.key`, `approval.key`, `/etc/virp/autopilot.env`,
`/run/virp/devices.json`. The systemd unit additionally masks all of
those paths (`InaccessiblePaths=`), sandboxes the filesystem
(`ProtectSystem=strict`), and grants write access only to the backup
tree.

Consequences of holding no O-Key:

- The runbook **cannot verify** observation HMACs; it stores the raw
  signed bytes (`signed_observation_b64` in each `.meta.json`) for any
  key holder to verify (`virp-tool inspect`, or the daily chainwalk).
  This is the deliberate trade documented in the autopilot units:
  under symmetric HMAC, a verifier needs the signing key, so the
  least-privilege client stores evidence instead of pretending to
  check it.
- The runbook **cannot approve its own proposals**: it holds no
  approval secret, is not in `/etc/virp/approvers.json`, cannot read
  the approvals store (0700 `virp`), and its source contains no
  approval code path (pinned by test — its action vocabulary is
  exactly `execute` and `chain_append`).

## Baselines — explicit adoption only

Baselines are established **only** by the operator command:

```
sudo -u virp-backup python3 /opt/virp/autopilot/virp_config_backup.py \
    set-baseline <device> [--from <backup.conf>|latest]
```

This copies a previously recorded (signed, chain-registered) backup to
`baseline.conf`, writes `baseline.meta.json` provenance, and registers
a `baseline_set` chain entry. The hourly run never writes
`baseline.conf` — a first run with no baseline alerts rather than
trusting whatever it sees.

## Responding to a drift alert

The alert and the `drift_alert` chain entry carry the
`restore_proposal_id` and the diff artifact path. A human decides:

- **Approve + apply** (within the proposal TTL, 300 s):
  `virp approve <id>` (as the enrolled approver) then
  `virp apply <id>` (as an allowlisted uid). Or re-run the shown
  restore command yourself through your own session — either way the
  action is yours, not the runbook's.
- **Reject** — do nothing; the proposal expires single-use at TTL.
  Then either investigate the change or bless it:
  `set-baseline <device> --from latest`.

If the diff can't be expressed as one safe revert command (nested
blocks, quoting, size), the alert says so (`note`) and no proposal is
filed — the diff artifact is the handoff to the human.

**Review the revert command before approving.** It is generated by
naive negation (`no <line>`), which is best-effort FRR syntax: it is
right for whole blocks and multi-instance lines, but single-value
attributes drop their argument in the no-form (observed live
2026-07-30: reverting ` description X` needs `no description`, not
`no description X`, which FRR rejects as unknown). An approved-but-
invalid revert fails harmlessly at the device with an error in the
signed outcome — but rejecting and restoring by hand is always the
cleaner path when the command looks off.

## Files

| Path | What |
|---|---|
| `autopilot/virp_config_backup.py` | the runbook |
| `deploy/virp-config-backup.service` / `.timer` | hourly unit (User=virp-backup) |
| `deploy/config-backup-access.sh` | ACLs + backup dir; fails loud on a mis-provisioned identity |
| `deploy/virp-onode-runbook.dropin.conf` | virp-onode ExecStartPost drop-in that runs the access script at each daemon start (socket + ACLs are recreated then) |
| `tests/test_config_backup.py` | behavior + policy tests (`make test-config-backup`) |
| `/var/lib/virp/config-backups/<device>/` | `<ts>.conf`, `<ts>.meta.json`, `drift-<ts>.diff`, `baseline.conf`, `baseline.meta.json` |
| `/var/lib/virp/config-backups/alerts.jsonl` | alert sink (journal is the other) |

## Deploy (virp-lab)

```
useradd --system --shell /usr/sbin/nologin --home-dir /nonexistent \
        --no-create-home virp-backup
install -m 0644 deploy/devices.template.json /etc/virp/devices.template.json
install -m 0644 deploy/virp-config-backup.{service,timer} /etc/systemd/system/
install -d /etc/systemd/system/virp-onode.service.d
install -m 0644 deploy/virp-onode-runbook.dropin.conf \
        /etc/systemd/system/virp-onode.service.d/50-config-backup.conf
systemctl daemon-reload
systemctl restart virp-onode   # new allowlist uid + ACL grant (drop-in)
systemctl enable --now virp-config-backup.timer
```

Retention: backups are kept indefinitely (~100 small files/day on this
lab). Prune by hand or add a tmpfiles.d age rule if it ever matters.
