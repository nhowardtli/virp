## P1 findings (2)

### P1-1. The public-key verifier accepts signed-but-malformed headers the v2 verifier would refuse

**Where:** `src/virp_crypto.c:883` (`virp_verify_observation_ed25519`) —
checks at lines 898 (version), 900 (channel), 908 (framing). Compare
`virp_verify_observation_v2` at `src/virp_crypto.c:~960`, which
additionally refuses `tier == VIRP_TIER_BLACK`, `tier > VIRP_TIER_RED`,
and `_reserved != 0`.

**Defect:** the v3 verifier validates version, channel, and exact framing,
then the signature — but not tier sanity or the reserved byte. A v3
observation with `tier = BLACK`, `tier = 0x7F`, or a nonzero reserved
byte passes public-key verification and is handed to the caller
(`hdr_out` propagates the values).

**Attack/impact:** only the signing-key holder (the daemon, i.e. the
attester) can mint such a blob, so this is not a consumer-forgeability
break. The exposure is forward-looking and real: the chain_append re-cut
will dispatch on this verifier, and "verified v3" will then mean *less*
header discipline than "verified v2" — a BLACK-tier observation, which v2
structurally refuses to accept, would verify as v3. Divergent invariants
between the two verifiers is exactly the class of gap the re-cut is
supposed to eliminate, and it is cheaper to close before the format is
load-bearing. The nonzero-reserved acceptance also forfeits forward
compatibility: a future flag bit in `_reserved` could not be introduced
fail-closed for v3.

**Proposed fix (not applied):** mirror v2's header sanity block in the v3
verifier — refuse `_reserved != 0`, `tier == VIRP_TIER_BLACK`,
`tier > VIRP_TIER_RED` — and add negative tests for each alongside the
framing negatives of P1-2.

### P1-2. No test feeds the verifier malformed framing — its reject paths have never executed, under ASan or at all

**Where:** tests `tests/test_obs_ed25519.c`, `tests/test_obs_ed25519_forge.c`
versus the reject paths at `src/virp_crypto.c:889-910` (short/oversize
`msg_len`, wrong version, wrong channel, lying `payload_len`).

**Defect:** every existing test calls the verifier with exactly-framed
input (genuine, byte-flipped, or signature-substituted — framing always
consistent). The framing rejects were verified by code reading only.
"all-tests green" and "asan green" therefore prove nothing about the
verifier's behaviour on truncated input, `payload_len` larger/smaller
than the actual buffer, `msg_len` between 0 and `VIRP_OBS_V3_MIN_SIZE`,
or a v2/v1 blob handed to the v3 verifier. This is the first surface a
hostile party probes, and the review instruction to "confirm ASan
actually exercised these paths with malformed input" fails honestly: it
did not, because no test constructs malformed framing.

**Attack/impact:** I traced the arithmetic and found it sound (see
non-finding NF-3), so this is a coverage/assurance gap, not a known bug —
but for code whose entire value is "a third party can run this on
untrusted bytes," untested reject paths are a merge-blocking gap, not a
nice-to-have.

**Proposed fix (not applied):** a `test_verifier_rejects_malformed_framing`
battery: every `msg_len` from 0 to `VIRP_OBS_V3_MIN_SIZE`-1 rejected;
`payload_len` ±1 and ±large vs actual; version bytes 0,1,2,4,255;
channel wrong; each asserting the SPECIFIC error code so a check firing
for the wrong reason fails the test. Run it under the (now-extended)
asan-test target. Optionally: a libFuzzer harness over
`virp_verify_observation_ed25519` — the function signature (pubkey +
byte buffer) is ideal fuzz shape, and `tests/fuzz_libfuzzer.c` already
exists as a pattern.

## P2 findings (4)

### P2-1. Docs do not state that ProVerif covers v2 only — the v3 path is not formally modeled

**Where:** SECURITY.md "Ed25519 Observation Signing (added 2026-08-07)";
`proofs/virp_obs_v2.pv`; README.md:351 (formal-verification claim,
correctly scoped to "accepted v2 observation" but silent on v3).

**Defect:** nothing in the Phase 2 docs claims formal verification of v3
— but nothing disclaims it either, and `make proofs` passing on a branch
whose headline feature is a new signature scheme invites exactly the
"machine-verified with no model" credibility trap this repo already
documented once (SECURITY.md's July correction culture exists for this
reason). A skeptical reader of SECURITY.md's v3 section next to
README's "machine-verified in ProVerif" paragraph can conflate them.

**Proposed fix (not applied):** one sentence in SECURITY.md's v3 section:
"The ProVerif model (`proofs/virp_obs_v2.pv`) covers the v2 HMAC scheme
only; the v3 Ed25519 path is NOT yet formally modeled." Add modeling v3
(sign/verify + downgrade queries) to the re-cut phase's checklist.

### P2-2. `virp-tool` never calls `virp_crypto_harden_process()` — keygen holds the secret in a dumpable process

**Where:** `src/virp_tool.c:156` (`cmd_keygen_obskey`); harden callers are
only `src/virp_onode_main.c:408` and `src/virp_onode_prod.c:725`.

**Defect:** during `virp-tool keygen obskey`, the Ed25519 secret exists in
a process that has not set `PR_SET_DUMPABLE=0`; a same-UID ptrace or a
core dump during that window exposes it. The secret is mlock'd (swap-safe)
but not dump-protected. Pre-existing class: `keygen okey/approval` and
`virp approve` have the same property, so this is not new to the branch —
but the branch added a new long-lived signing secret to that window.

**Proposed fix (not applied):** call `virp_crypto_harden_process()` at the
top of `virp-tool main()` (it is non-fatal by design), covering all keygen
and signing subcommands at once.

### P2-3. keygen writes the public key with `O_TRUNC` through a pre-existing path (symlink-followable)

**Where:** `src/virp_obskey.c:88` (`open(pk_path, O_WRONLY|O_CREAT|O_TRUNC, 0644)`).

**Defect:** the secret side is exemplary (`O_EXCL` 0600 from birth, no
chmod race — `src/virp_obskey.c:77`), but the `.pub` write follows an
attacker-planted symlink and truncates the target. Impact is low (content
written is public; requires a hostile file pre-placed at the exact pub
path the operator chose), and `virp_fed_save` has the identical pattern.
Consistency finding, not a custody break.

**Proposed fix (not applied):** `O_NOFOLLOW` on the pub write (and the
same in `virp_fed_save` while there).

### P2-4. Forge-contrast test 1 (HMAC ceiling) forges a v1 observation while tests 2–3 exercise v3 — pre-empt the apples-to-apples objection in the test comments

**Where:** `tests/test_obs_ed25519_forge.c`, `test_hmac_verify_key_holder_can_forge`.

**Defect (presentational, not technical):** the ceiling is demonstrated on
the v1 O-Key format (deliberately: that is the deployed scheme the
BGP-test finding was filed against) while the Ed25519 tests use v3. The
attested content class is the same (a fake device-output observation of a
never-received BGP route) and the claim being contrasted is about the
*scheme* (symmetric verify=forge vs asymmetric), which format does not
change — the v2 session-HMAC has the identical ceiling for a session-key
holder. But the file itself never says so, and a skeptic will raise it.

**Proposed fix (not applied):** a comment in test 1 stating why v1 is the
right reproduction target and that v2's session HMAC shares the ceiling;
optionally a fourth test forging a v2 observation with the session key to
close the gap empirically.

## Verified non-findings (recorded so the next reviewer need not re-derive)

- **NF-1. Cross-version downgrade is closed.** A v3 blob with its Ed25519
  trailer stripped keeps `version=3` covered by the session HMAC;
  `virp_verify_observation_v2` refuses it at the explicit
  `hdr.version != VIRP_VERSION_2` check (after HMAC, but refused).
  Relabeling byte 0 to 2 breaks the HMAC (byte 0 is covered). The v1
  parser (`virp_validate_message` → `virp_header_validate`) refuses
  `version != 1`. A v2 blob at the v3 verifier fails
  `VIRP_ERR_INVALID_VERSION` (and would fail min-size). Traced, and the
  HMAC-covers-version property is asserted by the byte-sweep test.
- **NF-2. The Ed25519 signature covers exactly `serialized_header ||
  payload`** — proven from code, not comments: build signs `out_buf[0 ..
  signed_len)` (`src/virp_crypto.c`, trailer-2 block) where the HMAC
  covers the identical span (trailer-1 block, same buffer, same
  `signed_len`); `tests/test_obs_ed25519.c`
  `test_signature_covers_exactly_canonical_bytes` pins coverage to ±1
  byte and excludes the HMAC trailer;
  `test_hmac_present_in_addition_with_v2_semantics` pins the HMAC to
  byte-identical v2 semantics.
- **NF-3. Framing arithmetic cannot wrap.** `expect = 88 + payload_len +
  96` with `payload_len` a `uint32_t`: no overflow on LP64; on ILP32 the
  short-circuit order (`payload_len > VIRP_MAX_MESSAGE_SIZE ||
  expect != msg_len`) rejects any payload_len large enough to wrap before
  `expect` is compared. `msg_len` is pre-bounded to
  `[VIRP_OBS_V3_MIN_SIZE, VIRP_MAX_MESSAGE_SIZE]`, so `signed_len` and
  the sig offset stay in-buffer. Every field read before signature
  verification (version, channel, payload_len) is bounds-relevant only
  and is itself covered by the signature subsequently verified.
- **NF-4. No path returns success on a bad signature.**
  `crypto_sign_verify_detached` returns 0 only on success; the sole
  `VIRP_OK` return in the verifier is behind that check. The forge tests
  assert the exact `VIRP_ERR_OBS_SIG_INVALID` code, so a length or
  version check firing first would fail the test — rejections are for
  the right reason. Wrong-key, zeroed, random (×64), and spliced
  signatures all rejected at the signature check.
- **NF-5. Test 2 attempts real attacks, not a strawman:** perfectly
  formatted v3 body; zeroed sig, random sigs, the genuine signature
  spliced from a real observation (valid signature, right key, wrong
  bytes), and a valid signature under an attacker-generated keypair.
  Sanity-check that the genuine observation verifies precedes the
  attempts, so a broken verifier cannot pass the test vacuously.
- **NF-6. The verifier touches no secret.** Its parameter list is
  `(public_key, msg, msg_len, out...)`; it reads no context, session, or
  key file. The `obs-verify` tool refuses a 64-byte (secret-key-shaped)
  file explicitly (`src/virp_tool.c:1871` ff.), demonstrated in the
  smoke run.
- **NF-7. Custody gate is complete per the checklist:** symlink
  (`O_NOFOLLOW`, `src/virp_obskey.c:113`), non-regular file (130),
  group/world bits (136), wrong owner (148), wrong size with distinct
  error (157), partial-read zeroization, EINTR-safe read loop, mlock
  with the repo's established non-fatal policy, `sodium_memzero` on
  destroy. The secret appears in no log/print/export path (error
  messages carry path and mode only). Secret written `O_EXCL` 0600 from
  birth — no chmod-after-write race, no world-readable window
  (0600 & ~umask can only tighten). Custody-inversion comment matches
  the code: the daemon loads the obskey secret; the approval path loads
  only `.pub` (see `cmd_keygen_approval`, unchanged).
- **NF-8. v1/v2 signing is byte-identical to main.** The branch diff
  contains zero deleted/modified lines in any existing function body;
  the only touched existing lines are usage strings, the `all-tests`
  list, and one added `virp_error_str` case. `test-obs-v2` (14 tests)
  and the core suite pass unchanged.
- **NF-9. Merge surface is the additive Ed25519 set only:** Makefile,
  SECURITY.md, docs/{DRAFT06-NOTES,VIRP-WIRE-FORMAT}.md,
  include/{virp,virp_crypto,virp_obskey}.h,
  src/{virp_crypto,virp_message,virp_obskey,virp_tool}.c, tests/×3.
  chain_append, gate, allowlist, approvals, consumed-list, obs_version
  defaults: untouched.
