# Release provenance — what a VIRP bundle proves, and how to check it

VIRP's pitch is signed provenance, so its own release archives are held to
the same standard. This closes a gap a reviewer found in August 2026: the
release ZIP was cut from tree `cd351af6` while the committed full-suite
report had tested `f200e621` (merged as `d21b465d`) — evidence that a
*nearby* tree passed, not that *this archive's* tree passed.

Every release published by `.github/workflows/release.yml` now carries:

| Asset | What it is |
|---|---|
| `virp-<tag>.zip` | `git archive` of exactly the tagged commit |
| `virp-<tag>.MANIFEST.sha256` | commit + tree hash, sha256 of the zip, sha256 of **every file inside it**, sha256 of the test attestation |
| `virp-<tag>.test-attestation.json` | machine-written full-suite result: the exact commit and tree the battery ran against, per-command exit codes, toolchain, timestamp |
| `virp-<tag>.MANIFEST.sha256.sig` | detached ed25519 ssh signature over the manifest by the operator release key (present when the `RELEASE_SIGNING_KEY` secret is configured, or added by the operator with `make release-sign`) |
| Sigstore attestation | keyless signature by the workflow's GitHub OIDC identity, always present |

The manifest is the single signing subject: it pins the bundle bytes, the
bundle contents, the commit, and the test evidence, so one signature over
the manifest covers all four. The pipeline is mechanical end to end —
`scripts/make-release-bundle.sh` **refuses** a test attestation whose
commit differs from the archived commit, refuses a dirty-tree run, and
refuses a failing result, so the original gap cannot recur for anything
this pipeline publishes.

## Verifying a downloaded bundle

One command (from a repo checkout, or with the three scripts copied out of
the bundle itself — they are inside it, and their hashes are in the
manifest):

```sh
scripts/verify-release-bundle.sh \
    --bundle virp-<tag>.zip \
    --manifest virp-<tag>.MANIFEST.sha256 \
    --attestation virp-<tag>.test-attestation.json \
    --signature virp-<tag>.MANIFEST.sha256.sig
```

This checks, in order: zip sha256 vs manifest; every bundled file vs its
manifest line **and** that the zip contains nothing the manifest omits;
that the attestation hashes to the manifest's `attestation-sha256`, names
the same commit, ran on a clean tree, and passed; and that the ed25519
signature over the manifest verifies against
`keys/release/allowed_signers` (identity `virp-release@thirdlevelit.com`,
namespace `virp-release`).

By hand, without the scripts:

```sh
sha256sum virp-<tag>.zip                      # compare to '# bundle-sha256:'
unzip virp-<tag>.zip
grep -v '^#' virp-<tag>.MANIFEST.sha256 | sha256sum -c
sha256sum virp-<tag>.test-attestation.json    # compare to '# attestation-sha256:'
grep '"commit"' virp-<tag>.test-attestation.json   # must equal '# commit:'
ssh-keygen -Y verify -f keys/release/allowed_signers \
    -I virp-release@thirdlevelit.com -n virp-release \
    -s virp-<tag>.MANIFEST.sha256.sig < virp-<tag>.MANIFEST.sha256
```

Sigstore (proves the artifact was built by this repo's release workflow on
GitHub's infrastructure, independent of any operator key):

```sh
gh attestation verify virp-<tag>.zip --repo nhowardtli/virp
```

`gh attestation verify` requires **gh 2.49 or newer** (the `attestation`
subcommand does not exist on older gh, including the 2.45 shipped by some
distributions). On an older gh, fetch a current one from
`github.com/cli/cli/releases`, or verify the Sigstore attestation with
`cosign`, or read it straight from the attestations API:

```sh
gh api repos/nhowardtli/virp/attestations/sha256:<zip-sha256>
```

A successful `gh attestation verify` prints `✓ Verification succeeded!` and
names the build workflow (`.github/workflows/release.yml@refs/tags/<tag>`),
the SLSA provenance predicate, and the GitHub Actions OIDC issuer. A stranger
verified v0.2.0 this way with gh 2.99.0.

## Continuous exact-head evidence

Independently of releases, every CI push runs the full battery under
`scripts/gen-test-attestation.sh` and uploads
`test-attestation-<sha>` as a workflow artifact — a commit-pinned,
machine-written test result for every head, so "which tree did this run
actually test?" is never answered from prose again.

## Operator pieces

- Release signing key: ed25519 ssh key, operator-held, **never** stored in
  the repo or generated by CI. Public half and `allowed_signers` are
  committed at `keys/release/`.
- `make release-bundle [RELEASE_REF=... RELEASE_DIR=... RELEASE_ATTESTATION=...]`
  — cut a bundle locally.
- `make release-sign MANIFEST=dist/<name>.MANIFEST.sha256` — sign a
  manifest with the operator key (`RELEASE_KEY`, default
  `~/.virp/release-signing.key`).
- `make test-release-tools` — selftests for all three scripts (runs as part
  of `make all-tests`), including an end-to-end that reproduces the
  original reviewer finding in miniature and proves the pipeline rejects
  it.
