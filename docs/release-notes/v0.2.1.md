VIRP v0.2.1: chain_append authorization is declared, and the build says what it is

A correctness release on v0.2.0. Two defects, both found by deploying
v0.2.0 to the production reference node and watching it refuse its own
evidence.

**v0.2.0 is WITHDRAWN from deployment. Do not deploy it.**

v0.2.0 ran on the reference node for ten minutes and fourteen seconds
(2026-09-02 02:16:00-02:26:14 UTC) and was rolled back. It carried the
Task 2 boot invariant — every allowlisted uid must have an action map —
on top of a pre-existing inference in the chain_append handler: any uid
merely present in socket_uid_action_allow was treated as a restricted
federated principal and narrowed to fed_request/fed_observation/
fed_outcome.

Mapping the daemon's own service accounts, which the new invariant
required, therefore reclassified them as federated principals. The node
began refusing its own appends — observation, comparator_verd,
chainwalk_summa, no_drift, evidence_item. Two individually correct
changes combined into a refusal of the node's own evidence, and there was
no template-only mitigation: the inference lived in the daemon, so no
configuration could exempt the service accounts.

The window itself is intact and accounted for: 16 gate_intent entries and
16 gate_execution closers, every execution closed, no open executions, no
chain break, no gap, and the evidence-degraded latch never tripped. What
was refused was appends, not executions. It is recorded as a dated
anomaly in DEPLOYED.md.

Fix 1 — chain_append reach is declared, never inferred.

- socket_uid_chain_append_types: an explicit per-uid list of artifact
  types. Enforcement is an exact string match. No substring matching, no
  prefix matching, no wildcards.
- A uid whose action set includes chain_append and which has no type list
  is a FATAL boot failure naming the uid, refused before the socket is
  bound. A forgotten list can no longer degrade into a silent narrowing.
- The netclaw bridge's fed_* reach becomes exactly one row of this
  policy. The inference is deleted.
- A malformed list loads as deny-all-types, fail closed.
- The listed spellings match the 16-byte wire field, so the truncated
  forms comparator_verd and chainwalk_summa are what the policy carries.

Fix 2 — the build id is a generated translation unit, not a per-TU macro.

v0.2.0 wrote node_config entries reading build_id="unknown" for its whole
window, so the chain could not say which source produced the daemon that
wrote it. The value was never missing: -DVIRP_BUILD_ID was placed on the
virp_onode_prod.c compile line, while the code that used it is archived
into libvirp.a and compiled without the define. A define on the wrong
translation unit produces no warning and no error.

- The id is now generated into a translation unit archived in the
  library, so every consumer links the same value.
- Resolution is git describe --always --dirty, then $VIRP_BUILD_ID, and
  otherwise a hard refusal to build. A build with no provenance is not a
  build worth shipping; inventing a placeholder is what v0.2.0 did.
- The prod daemon gains --version, answerable with no config, keys,
  socket or chain, so an installed binary can be identified in isolation.
- check-deploy-unit now also asks whether the installed binary matches
  the deploy tree that is checked out.

Testing.

The chain_append policy is pinned by replaying the real 30-day
(uid, action, artifact_type) traffic exported from the reference node:
v0.2.1 admits all of it, and the v0.2.0 semantics refuse the local
service appends. The regression is reproduced from real traffic rather
than asserted in prose, and again against the actual daemon handler.
Every new negative test was revert-checked against the pre-fix code and
confirmed to fail.

Known limitations (read before relying on this).

- The v0.2.0 limitations are unchanged and still apply. In particular the
  intent is durable against a process crash but not against power loss;
  that needs synchronous=FULL, which this build does not set.
- The type policy authorizes which types a uid may append. It does not
  weaken any gate validating the content of an append. Being on the list
  is permission to submit, never a waiver of verification.
- uid 1000's list is linted to cover every type virp-tool can emit, but
  that lint reads string literals in the tool source. It fails loudly
  rather than silently if the tool ever builds the type dynamically.
- The deploy build-id check is proven against a local fixture, not
  against the reference node, which was not reachable when this was
  written. It has not yet run against a real installed binary.
- This release has not been deployed anywhere.
